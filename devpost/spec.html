Technical Spec

The blueprint: a tiny Node/Express program serves a plain two-tab page, stores everything in one hand-editable JSON file, and checks the clock when you open it.

status: approved

How this works, in plain language

Four things, and that's the whole system:

  • A page you see — two tabs, Input and Issues, drawn by plain HTML/CSS/JS files you can open and read.
  • A small program that serves it — Node.js + Express answers localhost:3000 and handles small requests ("give me the issues", "save this").
  • A text file that holds everything — data/issues.json. Issues, manual order, and history are all plain JSON you can edit by hand.
  • A clock check, not a background service — open after noon and the program builds today's list if it hasn't; if the app is open at noon, the page asks for the same.

Why this shape: a browser page can't write your file on its own, and an always-running scheduler adds parts that are hard to debug. One local program + an on-open check keeps it to one command, one file, no accounts, no cloud.

    Issues + fieldsIn issues[]; re-read from the file on every load, so hand-edits show after refresh.
    Manual ordermanualRank per issue; lets a dragged position survive the next re-rank.

    Stack & dependencies

    • Node.js v18+ (v24 installed).
    • Express — the only runtime dependency. expressjs.com. Free, no key.
    • Built-ins — fs, crypto.randomUUID().
    • No database, hosting, APIs, accounts, keys, or cost.

    Start: npm install → npm start → open http://localhost:3000. Demo: add an issue, show the list and counters, drag one, complete one, edit data/issues.json, refresh, show it changed. No deployment.

    Where it will realistically break

    • issues.json is missing → the program creates an empty one; first run just works.
    • issues.json is malformed (a hand-edit broke the JSON) → it will not overwrite it; you get a plain message naming the file and the parse error so you can fix it.
    • Invalid input on the Input tab → a field-level error; nothing is saved.
    • Never opened for days → no list is made for those days; the next open makes one list for that day (agreed behavior).

    What was simplified, and why

    • On-open check instead of a background scheduler — same visible behavior, no daemon to debug.
    • One JSON file instead of a database — keeps the data hand-editable (the kernel).
    • No framework or build step — keeps every file readable and directly editable.
    • Native drag-and-drop instead of a library — one feature, well supported, no dependency.
    • Local-only, no deployment — the demo is a video + repo; hosting proves nothing extra.

    Decisions & open issues

    Your choices:

    • Node + Express + plain HTML/CSS/JS, local-only — one language, no build step, hand-editable. Tradeoff: more manual wiring.
    • JSON file storage — structured and standard. Tradeoff: malformed JSON needs graceful handling.
    • Settings in code, issues in the file.
    • On-open noon check, not a background service.

    Uncertainty discussed: how "noon" works without a background process — clarified by the on-open check. Verify in build: open after noon on a fresh date and confirm exactly one generation (counts +1 once; reopening doesn't double-count).

    Open issues:
    • Resolved during build: the comparator now sorts by days since creation first, then urgency, then difficulty, then deadline; the two-day deadline window was removed. See the build checklist's Revisions.
    • The manual-order rule is the subtlest behavior — build and verify it first, before the rest of the list features.
